# S1 review guide

This guide is for the three review sittings of M1.md §3.17 (G1 item 7). It covers the S1 code at commit **5381504**: every line number is a line of that commit. A bare `:N` is line N, and `:N-M` lines N to M, of the file that the table (or table section) is about. A line of any other file is written with that file's name, such as `machine.c:490` or `NativeMachine.java:129`. In a list that starts with such a name, such as `NativeMachine.java:102, :201`, each later bare `:N` is a line of that named file, up to the next semicolon, the closing parenthesis around the name, or the end of the sentence. `M1.md:N` is a line of M1.md at that commit too: the step 6 notes add lines only after line 770 and change line 54 (F14) in place, so lines up to 770 keep their numbers in this version.

For each function there is a call table: the thread that runs it, its run-context tag (C) or its use of the lock (Java), the calls in it that can raise a Lua error or throw a Java exception, and what to check there. Before each table, a second table says where to check each item of the sitting's checklist (C1–C11, J1–J6, L1–L5 in M1.md §3.17 and §3.9).

How the tables were made: one agent per part of the code wrote a draft from the source, and a second agent re-derived every row from the source and corrected the draft. Two more review rounds then checked the whole guide, and their corrections are in. The main session checked the findings in the source. The tables are still a guide, not proof: where a table and the code disagree, the code is right, and the difference is a finding.

## The rules in short

**Run-context tags** (M1.md §3.3 item 6, §3.8). Every C function has one in its comment:

| Tag | May do |
|---|---|
| `UNPROTECTED` | Only calls that cannot raise a Lua error. `cm_new`, `cm_load`, `cm_resume`, `cm_message` and `cm_free` run outside any `lua_cpcall`: a raise there ends the process (on Linux after LuaJIT calls `cm_panic`, §3.7). Helpers that must not raise carry this tag too, even when a `PROTECTED` body calls them, such as `msg_set` and `append_traceback` (D7). |
| `PROTECTED` | Calls that can raise (the "yes" rows of §3.8): it runs inside a `lua_cpcall`, which catches a raise and returns a status. It still makes no call from the "never in S1" row, and on `co` it makes only the calls of the rule for `co` (§3.7). Helpers that run only inside a `lua_cpcall` body, where a raise is caught, carry this tag too: `open_lib`, `jit_security`, `need_table` (also called from `build_apis`, `machine.c:614`), `remove_field`, `build_apis` and `render_error` (which itself raises nothing, `machine.c:788`) (finding 10). A helper that must not raise is `UNPROTECTED` even when only a `lua_cpcall` body calls it, such as `append_traceback` (row above). |
| `LUA_CFUNCTION` | `api_call`, which Lua calls, and `push_value` (`machine.c:460`), which only `api_call` calls; `raise_text` (`machine.c:453`) is tagged `PROTECTED or LUA_CFUNCTION`, because both kinds call it. A `LUA_CFUNCTION` function may raise only in phases 1 and 3 of `api_call`. Phase 2 calls Java and must not raise, because a raise there would unwind through the JNI frames. |
| `NO_LUA` | `jni_machine.c`: no Lua call at all. |

**JNI in five sentences** (M1.md §3.9). A JNI call that fails, or a Java method that it calls and that throws, leaves a Java exception *pending* on the thread; many calls also return NULL or a negative number then, but a NULL from `CallObjectMethod` can also be a plain `null` return. While one is pending, almost no other JNI call is allowed, so after each call that can throw, the code must check (`ExceptionCheck`, or a NULL or negative result where only a failure gives one) and clear it (`ExceptionClear`) before the next JNI call (J1). A native method must never return to Java with an exception pending (J4); none of these native methods throws on purpose (J3 forbids `ThrowNew`). Every Java object a native function gets back is a *local reference*, which stays alive until the native method returns, so a loop of upcalls must free them, here with one `PushLocalFrame`/`PopLocalFrame` pair per upcall (J2). `-Xcheck:jni` makes the JVM check some of these rules on every JNI call: it prints `WARNING in native method` (for example for a call made with an exception pending), or prints `FATAL ERROR in native method` and stops the JVM; the scan fails a run on any line that matches `natives/tests/jni-warnings.txt` (4 patterns), and a non-zero exit code fails it too.

What `-Xcheck:jni` does not see, so the review must find it: a leaked local reference (J2, M1.md F13); a missing `ExceptionCheck` after a `SetByteArrayRegion` or `GetByteArrayRegion` that did not throw (M1.md §3.17); and a native method that returns with an exception pending (J4), because that is legal JNI.

## Findings made while writing this guide

None is high or medium: each code finding needs an out-of-memory error, an addon that throws in an unusual way, an I/O error during a cleanup, a racy publication that no code does today, or a malformed message that `jni_machine.c` never builds (finding 4), and the rest are missing tests or wording.
