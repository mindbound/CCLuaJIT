## 1. Your review, checked

You asked whether you misread anything. The check: one agent per part of the review (R1 to R6, the documentation section, the checklist table, the validation section) compared every claim with the code and the CC:T 1.121.0 sources. A second agent then tried to refute each mistake that the first one reported. 37 agents in all.

**No claim of the review is wrong.** The line numbers, mechanisms and severities hold. Your Tier 0 numbers (166 checks, 0 of 7,684 accounting checks differ, 1,102 tracebacks) are the ones in the G1 logs of 5381504 (commit bf1aff2). The Ubuntu logs there show 165 because under ASan the memory check does not run: the test prints the memory figures as an info line, which is not counted. Some statements are narrower or wider than the code:

| Review | What the code shows |
|---|---|
| R1, trigger (line 23) | The race does not need the two calls to overlap in time. No happens-before relation orders the refused call's write and the owner's later writes, or the owner's later read through `nMessage`. Overlap in time only makes the damage visible. The existing cross-thread test is race-free because its seq_cst handshake (`blocked`, then the gate) orders the accesses. |
| R1, resolution (line 33) | Not writing is not enough on its own. JNI and Java read the message after every INTERNAL result and cannot tell busy from the other causes, so a refused caller on another thread would still race with the owner when it reads. Busy needs a channel of its own. Step 7 adds the status `CM_ST_BUSY`, and Java does not read the message for it. |
| R1, impact (line 27) | Right as a statement about C. With today's callers, a refused write stores 15 bytes at offset 0, and `msg_append` gets at most 511 bytes. So the likely outcome is garbled text, or `msg_tb` above `msg_len`, which `nMessage` already sends as "no traceback". An out-of-bounds write needs the compiler to exploit the undefined behaviour. |
| R3, triggers (lines 65, 75) | An undeclared `IOException` or `MachineException` leaves the constructor as a declared type, which CC:T handles normally. Only other checked types escaped, so the test uses `TimeoutException`. |
| R4, impact (line 89) | CC:T does close the machine. `ComputerThread` catches the throwable (`ComputerThread.java:642-645`) and calls `abortWithError`, and `immediateFail` calls `machine.close()` (`ComputerExecutor.java:254-256`). So the guide's "Nothing leaks" holds with CC:T, and only `handleEvent` itself did not close. A simpler path than R4's two failures: on every YIELD, `handleEvent` built a fallback `Wire.Message` outside any `try`, so one `OutOfMemoryError` there left the machine open until CC:T closed it. |
| R6, impact (line 125) | A restart helps only for a transient error. Each JVM runs the cleanup again on its first load, so a lasting listing error came back on every start. Also, apart from R6, the cleanup deleted other versions' directories without knowing whether another JVM was about to load from one. A JVM of another CCLuaJIT build that shares the cache, caught between its check and `System.load`, could fail for good. |
| Documentation (lines 135, 136, 142) | Guide finding 10 is about both tag definitions and the `M1.md` §3.3 table, not `PROTECTED` only. "The header" at line 136 is `machine.c`'s file comment, and it also left out `lua_type` and `lua_tolstring` on a string (only `lua_checkstack` is used on `co`). `cclj.c` also uses `lua_sethook`, the fourth name of the list that does not apply to it. |

## 3. Not fixed, or not tested

Lines of `jni_machine.c` and the Java classes that no test reaches after step 7:
- the lines of Sitting 2 (unchanged);
- `LuaJITMachine`: the `catch (Throwable)` and INTERNAL branches of `handleEvent`. Only a fault reaches them: an `OutOfMemoryError` inside `resume`; a JNI failure in `nResume`, a malformed `nMessage` array or `ST_BUSY`. The refused event needs an event, and `LuaJITMachine` passes none. Also the natives check of the constructor (every runner loads the natives first), the out-of-range index in `call` (the native side never sends one), the `IDynamicLuaObject` test of `unknown` (no test returns one), its cap of 256 logged classes, the fallback for a missing message in `handleEvent` (dead code: `resume` gives a message with every status but YIELD), and `printExecutionState` (CC:T calls it only in its report of a computer that overruns its time);
- `NativeMachine`: every `ST_BUSY` path, which only a broken lock reaches (the text in `create`, dead code because the handle is not published before `nLoad`; the branch of `resume` and `abandon`; the refused free and its log), and the malformed-message path of `ended` inside `resume` (`bridgeProbe` tests `ended` directly);
- `NativeLoader`: `intact` when the file goes away during the check, the per-directory catch of `cleanupStale` (the test's failing filter throws from the outer listing), and, as before, the failed move on Windows, an unsupported platform, the aarch64 and macOS arms of `platformId` and `libraryFileName` (every test host is Windows or Linux x86_64), a build without natives, and the `NoSuchAlgorithmException` catch (every JVM has SHA-256);
- `NativeLibrary`: the `VirtualMachineError` catch of `ensureLoaded` and the `RuntimeException` and `Error` arms of `rethrow` (the sticky-failure test fails with an `IOException`), and its `IllegalStateException` arm (dead code: only an `IOException`, `RuntimeException` or `Error` is kept);
- `Wire`: the limit of 65,536 methods in `SpecWriter.method` and the 2 GiB cap of the writer;
- `CCLuaJITCommon`: no test calls it. Only the NeoForge entry point calls `init`, so `init` (also called a second time), `nativesAvailable` with its fallbacks, and `logQuietly` run only in the game (S8 checks the fallback).

`machine.c` also has defensive lines that valid use never reaches, so Tier 0 does not run them, for example the `CCLuaJIT: machine missing` raises of the three `lua_cpcall` bodies, the raise of `need_table`, the check of the security defaults, the failed growth of the bios coroutine's stack in `load_body`, the F4 state check of `resume_body` and its missing error value.

Not fixed:
- An allocation failure while the constructor builds its `MachineException` can still escape. No ordering of catch blocks can prevent that.
- The cleanup can still delete a directory between the mark and `System.load`, when another JVM read the old time just before the mark and deletes just after it. That needs two different builds sharing one cache root, and a delete within the moments that the check and the load take. A file that is gone at the check is extracted again.

Not possible: the whole Tier 0 program under ThreadSanitizer. It ends with a segmentation fault and no TSan report, after the last check of section 2 and before section 3 (the spec fuzz) prints its check. So the race was checked with the harness in the artifacts.
